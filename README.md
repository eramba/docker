Welcome to eramba's official Github account, for Docker installs please review our website Learning Platform ([eramba.org](https://www.eramba.org/learning/courses/12/episodes/274)) under Docker Install.

The bundled files in `apache/ssl/` are a branded local development certificate intended only for local or simple demo installs. It is signed by a local development CA and will only be trusted on machines where that CA has been installed. Replace it with your own CA-issued certificate and private key for any real deployment.

Eramba and its MCP endpoint share the `PUBLIC_ADDRESS` origin. With the default configuration the application is available at `https://localhost:8443` and MCP at `https://localhost:8443/mcp`; issuer, resource, metadata, and OpenAPI URLs are derived automatically. Do not add separate public MCP URL variables.

Before starting a real deployment, replace `OAUTH2_INTROSPECTION_CLIENT_SECRET` in `.env` with a unique random secret. `ERAMBA_MCP_IMAGE_TAG` defaults to the latest MCP image and can be pinned when required.

## Client IPs and trusted reverse proxies

**Image dependency:** this configuration requires an Eramba image that implements the `TRUSTED_PROXIES` Apache startup configuration. Publish and verify that image for the installed edition before rolling out these installer changes. Existing images without this support do not make `TRUST_PROXY=1` safe. The Compose files still use `latest`; a tag named `latest` alone is not evidence that it contains the change. Pin a verified compatible release or image digest using your deployment's Compose override. There is no new release version assigned in this repository.

The request path is client → optional external load balancer → bundled Caddy → Eramba. Caddy resolves `X-Forwarded-For` from right to left and sends one client address to Eramba. Apache trusts only Caddy's fixed IPv4 address, normalizes the request's client IP, and supplies that same address to CakePHP and Laravel. No application configuration or PHP changes are required.

Configure these installer values in `.env`:

| Variable | Default | Meaning |
| --- | --- | --- |
| `APP_INTERNAL_SUBNET` | `172.30.250.0/24` | IPv4 CIDR for the existing `app_internal` network. Choose a non-overlapping network. |
| `APP_INTERNAL_DYNAMIC_RANGE` | `172.30.250.128/25` | Subrange for automatically allocated container addresses, inside `APP_INTERNAL_SUBNET` and excluding `PUBLIC_PROXY_IP`. |
| `PUBLIC_PROXY_IP` | `172.30.250.2` | Fixed Caddy IPv4 address inside the subnet but outside the dynamic range; it must not be the network, broadcast, gateway, or another container's address. |
| `EXTERNAL_TRUSTED_PROXIES` | empty | Space-separated external load balancer IPs/CIDRs; both IPv4 and IPv6 are supported. Empty means no external proxy is trusted. |

Compose derives the application's `TRUSTED_PROXIES` as `${PUBLIC_PROXY_IP}/32` and sets `TRUST_PROXY=1`; do not put external load balancer networks in the application's list. `TRUSTED_PROXIES` is the image's comma-separated interface, whereas `EXTERNAL_TRUSTED_PROXIES` is Caddy's **space-separated** interface. The Enterprise overlay inherits the same network and trust settings. The `USE_PROXY`/`PROXY_*` settings describe an outbound proxy and are unrelated.

For example, if only the load balancer at `192.0.2.10` connects to Caddy, set `EXTERNAL_TRUSTED_PROXIES=192.0.2.10/32`. For multiple trusted hops, list the actual controlled proxy addresses or narrowly scoped CIDRs, separated by spaces. Configure the external edge to overwrite client-supplied forwarding metadata, or to append its observed client to `X-Forwarded-For`; each trusted hop must sanitize the other forwarded headers it supplies. Do not use a wildcard, all-address ranges, or broad private networks merely to make an address appear correctly.

Caddy ignores incoming `X-Forwarded-For`, `X-Forwarded-Proto`, and `X-Forwarded-Host` from untrusted peers. It also removes their `X-Forwarded-Port`, `X-Forwarded-Prefix`, `Forwarded`, `X-Real-IP`, and `Client-IP`. Legitimate metadata from configured external proxies is preserved. Underscore and dot aliases of these headers are always removed, including on MCP paths. This trust decision uses the original connection peer, independently of the resolved client IP.

Docker checks that the fixed IPv4 address and dynamic range belong to the network subnet and rejects invalid or conflicting allocations when creating the network/container. Keep Caddy outside the dynamic range so earlier-starting services such as MySQL cannot take its address; do not reserve it with `aux_addresses`, which also prevents Caddy from claiming it. `docker compose config --quiet` checks Compose interpolation and structure only; it does not prove that a subnet is available or that the static address is outside the dynamic range. Review existing Docker networks, LAN/VPN routes, and other installations before choosing a subnet. Caddy refuses malformed external IP/CIDR entries at startup.

### Updating an existing installation

This update does **not** migrate or renumber an existing Docker network automatically. Adding explicit IPAM/static addressing requires a planned stack restart. Keep a backup of the previous Compose files, Caddyfile, `.env`, and image digests, and use your normal database/data backup procedure first.

1. Before replacing the running configuration, identify the current `app_internal` network and its allocated addresses. `docker network ls --filter label=com.docker.compose.network=app_internal` may show several projects; select the network belonging to this installation, then inspect it with `docker network inspect <network-name>`. Record its subnet and gateway and check every attached container. If unrelated containers use it, coordinate their removal instead of forcing a disconnect or deleting the network.
2. Prefer preserving the current subnet: set `APP_INTERNAL_SUBNET` to its actual CIDR, choose an unused, non-gateway `PUBLIC_PROXY_IP` within it, and set `APP_INTERNAL_DYNAMIC_RANGE` to a subrange excluding that address with enough room for the other services. For example, subnet `10.70.8.0/24`, dynamic range `10.70.8.128/25`, and Caddy `10.70.8.25` keep those allocations separate. The new default `.2` may already belong to MySQL or another container in an existing installation. Other containers receive addresses from the new dynamic range when recreated, even if the overall subnet is preserved. Review rules depending on individual addresses. If a different subnet is necessary, also check for collisions and update external firewall/network rules that depend on the old network. Do not copy the defaults over a running deployment without this check.
3. Confirm that the selected Eramba image contains the Apache trusted-proxy startup support, including `/usr/local/bin/configure-trusted-proxies.php` and its entrypoint integration. Pull the verified image before the maintenance window. Keep the same Compose project name, working directory, overlays, and volume configuration throughout the update, so the application and database keep their existing named volumes.
4. Render the updated configuration without displaying secrets: `docker compose -f docker-compose.simple-install.yml config --quiet`. For Enterprise, include `-f docker-compose.simple-install.enterprise.yml` in this and every subsequent Compose command.
5. During the maintenance window, run `docker compose -f docker-compose.simple-install.yml down` **without `-v`**. This removes the project's containers/networks but preserves the named application and database volumes. If Docker reports remaining network endpoints, resolve their ownership before proceeding; do not prune volumes or force-remove a shared network.
6. Run `docker compose -f docker-compose.simple-install.yml up -d` with the same project identity and overlays. Inspect service status and Caddy/Apache startup logs, then verify application access, HTTPS URLs, MCP access if used, and the client IP from a real request through the intended ingress. Confirm direct forged forwarding headers do not alter that client IP or generated URL. Test the configured external load balancer separately if one is used.

To roll back the network/configuration change, stop the stack with `down` **without `-v`**, restore the saved files and prior image references, and recreate it with the same project identity and volumes. The previous implicit network configuration may select a different subnet when recreated; use the recorded subnet in a temporary IPAM override if exact restoration is needed. Rolling back installer files does not roll back application database migrations; follow the Eramba release's rollback procedure if the image update changed the database. Never delete the data volumes to resolve a networking error.

### Configuration tests

Run `npx --yes bats@1.12.0 tests/*.bats` with Docker, Compose, `jq`, and `curl` available. Compose checks use dummy credentials. Caddy checks use the existing `caddy:2.8-alpine` version in temporary containers with random localhost ports and remove those containers afterward; they do not start MySQL or an Eramba application stack. The allocation test also creates and removes a temporary internal network using the default installer subnet, which must be unused on the test host, and starts two dummy dynamic services before claiming Caddy's static address.
